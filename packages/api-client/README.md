# `@aivo/api-client`

Typed bindings for AIVO backend services, generated from each service's
Fastify-emitted OpenAPI document. This package contains **types only** —
it deliberately ships no runtime client. Web (`apps/web`) and mobile
(`apps/mobile`) keep their existing `apiFetch` helpers and import
request/response shapes from here.

## Phase 5 staging

This is the Phase 5.0 foundation slice:

- The package skeleton, dump script, generator, and CI drift check exist.
- One service (`identity-svc`) is already wired through the pipeline as
  the seed.
- **No callers have been migrated.** That work happens per-service in
  the 5.1+ slices and lets each migration land in a small, reviewable PR
  rather than one giant cross-cutting change.

## Layout

```
packages/api-client/
├── openapi/                # committed JSON dumps, one per service
│   └── identity-svc.json
├── src/
│   ├── index.ts            # auto-generated barrel of namespaces
│   └── identity-svc.d.ts   # auto-generated by openapi-typescript
└── README.md
```

Both `openapi/<svc>.json` and `src/<svc>.d.ts` are generated and
committed. CI (`.github/workflows/api-client-drift.yml`) regenerates
them on every PR and fails if the working tree differs from what was
committed, so the spec on disk is always in sync with the route schemas
in the corresponding service.

## Pipeline

```
service Fastify routes (with @fastify/swagger schemas)
        │
        ▼  pnpm api:dump
packages/api-client/openapi/<svc>.json
        │
        ▼  pnpm api:generate     (runs api:dump first)
packages/api-client/src/<svc>.d.ts
        │
        ▼  callers import { paths, components }
apps/web, apps/mobile
```

Root scripts:

| Command              | Purpose                                                         |
| -------------------- | --------------------------------------------------------------- |
| `pnpm api:dump`      | Boot each registered service in-process, write `openapi/*.json` |
| `pnpm api:generate`  | Run `api:dump`, then `openapi-typescript` per spec              |
| `pnpm api:check`     | Run `api:generate`, fail if `git diff` is non-empty             |

`api:check` is the CI gate.

## Consuming the types

Once a service has been onboarded:

```ts
import type { paths } from "@aivo/api-client/identity-svc";

type LoginBody = paths["/api/auth/login"]["post"]["requestBody"]["content"]["application/json"];
type LoginRes  = paths["/api/auth/login"]["post"]["responses"]["200"]["content"]["application/json"];

const res = await apiFetch("/api/auth/login", { method: "POST", body: JSON.stringify(body) });
const data: LoginRes = await res.json();
```

No runtime is shipped: `apiFetch` continues to live in each app.

## Onboarding a new service (5.1+)

1. **Make the service dumpable.** Refactor `services/<svc>/src/index.ts`
   so the Fastify app is built in an exported `buildApp()` function (see
   `services/identity-svc/src/index.ts` for the reference shape). The
   `start()`/`listen()` call must not happen at module top level.
2. **Register `@fastify/swagger` + `@fastify/swagger-ui`** if missing.
3. **Add per-route schemas** (`schema: { body, params, querystring,
   response }`) — without these, the dump emits an empty path object.
   Use **non-strict** response mode initially so existing handlers keep
   passing.
4. **Register the service** in `scripts/dump-openapi.mjs` by appending
   an entry to `SERVICES`.
5. Run `pnpm api:generate` and commit the new `openapi/<svc>.json` and
   `src/<svc>.d.ts`.
6. Migrate callers off any inline `interface XYZResponse { ... }`
   declarations in `apps/web` and `apps/mobile` onto the generated
   `paths` types. This step is what makes the typing actually
   load-bearing.

## Risks / things that bit us

- `@fastify/swagger` will silently emit `{}` for routes without a
  `schema` block. The generated client will compile but be useless.
  Always add at least a `response` schema.
- Strict response validation can reject responses that include fields
  not declared in the schema. Land schemas with the default loose
  response mode first and tighten later.
- Booting a service for the dump pulls in real plugins (DB, MFA key,
  rate-limit). The dump script sets stub env vars (`DATABASE_URL`,
  `MFA_AT_REST_KEY`, `NODE_ENV=test`) so `buildApp()` succeeds without
  hitting Postgres. Service refactors should keep DB queries lazy
  (driver-level, not at boot).
